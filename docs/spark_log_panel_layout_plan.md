# 「本地服务工作日志」布局重构方案

> **状态：已落地**（2026-07-29）。实施中发现两件计划时不知道的事，都改变了做法，
> 见 [九、落地时的偏差](#九落地时的偏差)。原方案正文保留原样，便于对照。

目标：把一个**终端 tail 窗**，换成"**上面一句人话结论 + 下面几张可操作的事件卡**，
原始日志退到第二个标签页"的两模式面板。同时在服务端把噪声从源头砍掉——
面板里 81% 的行是 HTTP 访问日志，任何前端筛选都只是在给一条脏流做事后打捞。

对照现状：[index.html:1614-1659](../index.html#L1614-L1659)、
[js/api_client.js:374-870](../js/api_client.js#L374)、
[css/app/panels-tabs.css:1998-2385](../css/app/panels-tabs.css#L1998)、
[server_common.py:123-270](../server_common.py#L123)、
[server.py:1700](../server.py#L1700)。

## 一、先看实测数字，不是感觉

对当前 `server.log`（43,284 行）做分类统计：

| 类别 | 行数 | 占比 | 谁产生的 |
|---|---:|---:|---|
| HTTP 访问行 `LOG: "GET /outputs/… 304 -"` | 35,249 | **81.4%** | [server.py:1700](../server.py#L1700) `log_message` |
| 未迁移的裸 `print()` / 异常回溯 / ANSI 彩框 | 6,888 | 15.9% | 各模块（server.py 48 处、frame_generator 23、video_generator 19…） |
| 结构化 `log()` 行（有级别/tag/task） | 1,147 | **2.6%** | [server_common.py:243](../server_common.py#L243)，仅 10 个 tag |

**结论先行**：面板费了很大力气做的级别徽标、任务过滤、重复折叠，只对那 2.6%
有效。剩下 97.4% 全部落进 `OTHER` 级别，而 `OTHER` 默认是开着的
（[api_client.js:450](../js/api_client.js#L450)）。用户打开面板看到的就是一屏
`GET /outputs/%E5%BA%9F%E5%BC%83…mp4 304`。

再看那 6,888 行里最高频的几种形状：

```
328×  LOG: Request timed out: TimeoutError('timed out')
199×  LOG: code 404, message File not found
 82×  ␛[0m[12:03:41] │ ℹ️ │ 账号池      │ ⏳ AdsPower 本地 API 限频（第 2 页），3.2s 后重试 1/5␛[0m
 64×  ────────────────────────────────────────␛[0m
 43×  Traceback (most recent call last):
 41×  [COLOR MATCH] Warning: LAB color matching failed: No module named 'cv2'
```

第 3、4 条里的 `␛[0m` 是真的 ESC 字节——`fx_console` 的彩色框线原样落盘，而前端
**没有任何 ANSI 剥离**（`js/api_client.js` 全文无 `\x1b` 处理）。也就是说面板里
现在肉眼可见地混着一堆 `[0m` 乱码和半截框线。这是"不够美观"最直接的那部分。

## 二、三层诊断

### 1）源头脏——这是主因，前端解决不了

访问日志、`404 File not found`、`Request timed out` 这三类占了压倒性多数，且对
"我的片子生成得怎么样"零信息量。它们该被降级或静默，而不是被筛掉。

### 2）面板把"筛选"当成了解法

顶部 `.log-panel-filters` 常驻**四行控件**（[index.html:1635-1655](../index.html#L1635-L1655)）：

```
[只看问题]  ERROR WARN INFO DEBUG 其他        ← 行1：1 按钮 + 5 芯片
[按任务 id 过滤（点行内任务标签快速填入）]     ← 行2
[搜索关键词...]                               ← 行3
[✓自动滚动]  [清空]        1247/3000 行       ← 行4
```

按当前 CSS（`padding 8px 12px` + 6px gap + 四行控件）约 **110px 常驻高度**，占
420px 宽 dock 可视区的一成多。而这四行全部是开发者词汇：`ERROR/WARN/DEBUG`、
`任务 id`、`3000 行（含折叠重复）`。不懂代码的人在这里一个控件都用不上，却必须
一直看着它们。

### 3）外观是给终端做的

- 整个 dock `font-family: Consolas/Courier`，背景 `#080a0f` 纯黑，与产品其余部分
  的视觉体系割裂。
- 每行铺 **5 段元信息**：`12:14:07  WARN  [账号池]  task=frames_aa3f…  正文`。
  时间戳精确到毫秒、`task=frames_aa3f2e9b4c1d…` 这种 hash——对排障有用，对
  "现在到底怎么了"是纯干扰，而且把正文挤到了行尾容易被换行截断。
- `word-break: break-all`（[panels-tabs.css:2212](../css/app/panels-tabs.css#L2212)）
  会在中文和 URL 中间任意断字，长 URL 行糊成一坨。

### 4）不该由它承担的事

「任务进行到哪一步」已经有专门的载体：`#tasks-drawer`（[index.html:1295](../index.html#L1295)）
+ [js/progress_model.js](../js/progress_model.js) 已经把 `outline/batch/audit/repair`
翻译成了「批量合成提示词 3/12」这样的人话。**本方案不重做进度**，日志面板只回答
另一个问题：**"有没有出事，出的什么事，我要不要管"**。

## 四、事件卡从哪来：一张语义映射表

新增 `js/log_semantics.js`（纯函数，无 DOM，可单测），把日志行归成**事件**：

```js
const LOG_RULES = [
  {
    id: 'adspower-rate-limit',
    match: /限频|限流|rate.?limit/i,
    severity: 'warn',
    title: '生图账号被限流',
    hint: '已在自动重试，通常几分钟内自行恢复，不用操作。',
    action: null,                       // null = 不需要人管
  },
  {
    id: 'cv2-missing',
    match: /No module named 'cv2'/,
    severity: 'error',
    title: '调色功能不可用（缺少 cv2）',
    hint: '成片仍能出，但各帧色调一致性会变差。',
    action: { label: '怎么修', href: '#/help/cv2' },
  },
  {
    id: 'upstream-timeout',
    match: /Request timed out|TimeoutError/,
    severity: 'warn',
    title: '上游响应超时',
    hint: '单次请求超时，任务会自动重试；连续失败才会中断。',
    action: null,
  },
  // …
];
```

每条规则四个字段回答用户的四个问题：**出了什么事**（title）、**严重吗**
（severity）、**意味着什么**（hint）、**我要做什么**（action，null 就明说不用管）。

**聚合键** = `rule.id + task`。同一规则同一任务的 N 条行合成**一张卡**，卡上标
`×N` 和首末时间——这正是现有 `shapeKey` 连续折叠（[api_client.js:487](../js/api_client.js#L487)）
的思路，但放宽成"不要求连续"，因为两次限流之间往往夹着别的行。

**兜底**：没有命中任何规则的 `ERROR` 行，仍然生成一张卡，title 用原始正文首 60
字，hint 固定为「未识别的错误，点开明细查看完整信息」。**宁可多出一张丑卡，不能
把错误吞掉**。命中不了规则的 `WARN/INFO/OTHER` 则完全不进概览——概览的准入门槛
就是"值得人看一眼"。

规则表按 tag 优先匹配（有 tag 的先按 tag 缩小范围再跑正则），未命中再全量扫，
避免 O(规则数 × 行数) 的全表扫描成为热路径。

## 五、服务端降噪：最大的那一刀

前端做得再好，也架不住 81% 的输入是垃圾。三处改动：

### 1. HTTP 访问日志按状态码分级（-81%）

[server.py:1700](../server.py#L1700) 现在无差别 `sys.stdout.write(f"LOG: …")`。
改成走结构化 `log()`，并利用已有的 `self._spark_status_code`
（[server.py:1709](../server.py#L1709) 已经记下了）：

- `2xx / 3xx` → `log('DEBUG', 'HTTP', …)`，非 DEBUG_MODE 下**直接不落盘**
  （[server_common.py:253](../server_common.py#L253) 已有这个短路）
- `4xx` → `log('WARN', 'HTTP', …)`
- `5xx` → `log('ERROR', 'HTTP', …)`

排障需要看全量访问日志时，开 `DEBUG_MODE` 即可，能力没丢。

### 2. 落盘时剥掉 ANSI（治那批 `␛[0m` 乱码）

`_Tee.write` 已经在向两个流扇出（[server_common.py:133-138](../server_common.py#L133-L138)）。
在写 `_rotating_log` 那一路上加一次 `_ANSI_RE.sub('', data)`——**控制台那一路不动**，
终端里的彩色框线照旧。一处改动，`server.log` 和面板同时变干净。

### 3. 高频噪声就地降级

- `code 404, message File not found`（199 次）：`end_headers` 已经在识别 404
  了（[server.py:1712](../server.py#L1712) 附近），静默 `/outputs/` 下的 404 探测。
- `[COLOR MATCH] Warning: … No module named 'cv2'`（41 次）：这是**同一个环境缺
  失被重复报了 41 次**。改成进程内只报一次（模块级 flag）。

### 4. 顺带：把剩下的裸 `print()` 迁到 `log()`

不是本次必做（113 处，量大），但每迁一处，概览模式就多认识一类事件。建议按
"被规则表引用到的优先"来排序迁移，而不是从上往下扫。

## 七、明确不做

- **不做进度展示**。那是 `#tasks-drawer` + `progress_model.js` 的职责，重复一份
  必然两处不一致。概览里的卡片只在"出事"时出现。

## 八、验收标准

1. 空闲 10 分钟后打开面板，概览模式应显示空状态，**不出现任何 HTTP 访问行**。
2. `server.log` 中不再含 ESC 字节（`grep -c $'\e' server.log` 为 0）。
3. 断开网络跑一次生成：概览出现「上游响应超时」一张卡（不是 328 张），

5. 明细模式的默认可视区高度比现在多约 74px（四行控件 → 一行）。

## 九、落地时的偏差

实施时发现三件计划阶段不知道的事，前两件改变了做法。

### 1. 前端的日志解析在 Windows 上一直是全废的（本次最大的一处）

`_LOG_LINE_RE` 对 **server.log 里的每一行都匹配不上**，所有日志无差别退化成
`OTHER` 级别——也就是说级别徽标、任务过滤、按级别着色、「只看问题」这套东西，
在 Windows 上从来没真正生效过。

根因是行尾：`RotatingFileStream` 以文本模式打开文件，Python 在 Windows 上把 `\n`
翻译成 `\r\n`（实测 `server.log` 43,589 个换行 **100% 是 CRLF**）；SSE 端按二进制
读、按 `\n` 切，于是每行都留着一个 `\r`。而 JS 的 `.` 不匹配 `\r`，末尾的 `$` 也
不会停在 `\r` 前面，整条正则必然失败。

这解释了"无效信息太多"里此前没算到的一大块：**连那 2.6% 的结构化行也没法按级别
筛**。修在 `appendLine` 里剥掉行尾 `\r`（[js/api_client.js:579](../js/api_client.js#L579)）。
这一条是既有缺陷，与布局无关，但不修的话概览的兜底卡永远不会触发（它要求
`level === 'ERROR'`），整个规则表只能靠正文关键词硬撞。

### 2. 访问日志不能挂在 `DEBUG_MODE` 上

原计划把 2xx/3xx 记为 `DEBUG`，理由是"非 DEBUG_MODE 下 `log()` 直接短路不落盘"。
但本机 `server_config.json` 里 `"debug": true`——照原计划做，降噪等于没做。

而且这不是个例：「我要看异常堆栈」和「我要看每一个 304」本来就是两个不同的需求，
把它们绑在一个开关上，正是日志一开 debug 就彻底没法读的原因。改为给访问日志一个
**独立开关** `logHttpAccess` / `SPARK_LOG_HTTP_ACCESS`（默认关），
见 [server_common.py](../server_common.py) 的 `http_access_logging()`。
4xx/5xx 里真正的异常不受开关影响，永远留痕。

实测：60 次请求（45 次 200 + 15 次 `/outputs` 404 + 1 次真 404）→ 日志从 59 行降到
7 行，只留下那条真 404 的 `WARN`；打开开关后访问日志原样回来。

### 3. dock 需要自带色板

dock 是硬编码的深色面（`#080a0f`），但它内部原先用的是**跟随主题**的 `--text-*`。
浅色主题下 `--text-primary` 是 `#2E2A24`（近黑），压在近黑底上对比度只有 **1.39:1**，
字直接糊成一片。旧版没暴露是因为 dock 里只有等宽日志行，用的是写死的 `#f8f8f2`；
一旦出现按主题取色的组件（按钮、输入框、事件卡）就全线不可读。

改为在 `.log-panel-drawer` 上定义一组与主题无关的局部色板
（`--log-fg` / `--log-fg-dim` / `--log-fg-mute` / `--log-accent` / `--log-edge`），
dock 区间内 28 处主题变量全部改指它。正文对比度 **1.39:1 → 16.45:1**，
次级文字与页脚也都过 WCAG AA（≥4.5:1），且深浅两种主题下观感一致。

### 验证方式

- `node tests/test_log_semantics.js`：规则表命中/聚合/兜底不吞错误/两处 key 一致。
  写这个测试时抓到一个真 bug——`order[a.severity] || 9` 里 `error` 的序号是 `0`，
  被 `||` 当成假值吃掉，卡片排序整个反了。
- Playwright 实机跑通完整链路（日志文件 → 增量读 → SSE → 前端 parse → 规则表 →
  事件卡），并逐项验证「查看明细」跳转定位+高亮、筛选浮层外部点击关闭、
  「只看问题」双向切换、模式记忆、Esc 收起。
- `pytest tests/`：1179 passed。
  （`tests/test_frame_start_preserves_completed.js` 在本次改动前即为失败，未处理。）
